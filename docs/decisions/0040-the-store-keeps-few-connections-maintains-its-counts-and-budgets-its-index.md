# ADR 0040 — The store keeps few connections, maintains its counts, and budgets its index

- **Status:** Proposed (2026-09-23)
- **Date:** 2026-09-23
- **Extends:** [ADR 0038](0038-the-store-is-turso-not-sqlcipher.md) (the engine), [ADR 0014](0014-encryption-at-rest.md) (the threat model, unchanged here), [ADR 0015](0015-threaded-list.md) (the threaded list), [ADR 0016](0016-full-mailbox-backfill-by-default.md) (full backfill)
- **Issues:** #1602, #1606, #1607, #1610, #1612, #1614, #1587, #1503
- **Decision:** **Three long-lived connections with a cache each, every per-page aggregate answered from a maintained column or a bound index range and gated on its plan, a materialised `(mailbox, thread)` table so a folder window is an index range, a one-line retained-budget patch on the engine's full-text index with the knob requested upstream, the page codec kept, and the allocator chosen by a measurement this ADR specifies rather than by argument.**

---

## Context

A live UI process measured 908–917 MB resident with a high-water mark of 960–977 MB, and its one mimalloc arena grew 591 → 640 → 671 MB while two large folders synced (#1602, #1606). `docs/PERFORMANCE.md` recorded 55 MiB of anonymous memory at 100,000 messages on the old engine, flat to 400,000. On felt speed: counting a 60,907-message folder's conversations costs **786 ms** (#1534; `crates/postio-runtime/src/store/local.rs:57-58`) and is paid again after every archive because the count witness moves (#1607); a scrollbar drag is an `OFFSET` over a correlated `NOT EXISTS` window (#1610; `crates/postio-storage/src/repository/threads.rs:1077-1083`); every search walks the account once backfill is complete (#1612; `crates/postio-index/src/executor.rs:462-486`); Flagged, Account and Unified pages run `count(*)` per page (#1614; `local.rs:577-589`). A first sync cost ~118 ms per row until #1587 found a collated index column the planner will not bind through, and the metadata full-text index still adds a constant ~9–13 ms per row inside the write transaction (#1587, comment of 2026-09-21). Three facts about turso_core 0.8.0-pre.11 sit under all of it. Every `Database::connect` builds its own `Pager` with `PageCache::default()` (`database.rs:2320` → `:3064-3068`; 2,000 pages, `storage/page_cache.rs:14`), and Postio's `PRAGMA cache_size = -65536` (`crates/postio-storage/src/store.rs:328`) raises each one to 64 MiB through `Connection::set_cache_size` → `Pager::change_page_cache_size` (`translate/pragma.rs:1920`, `storage/pager.rs:3754-3757`). A read transaction that follows any other connection's commit **clears its whole cache** (`storage/pager.rs:3198-3202`, with upstream's own comment: "we can probably do better with more granular invalidation"). And the `fts` index method assembles each segment file into an `Arc<[u8]>` in the heap (`index_method/fts/directory.rs:45,92`) and retains up to `FTS_MAX_RETAINED_CACHE_BYTES = 192 MiB` per attachment for reuse, with no pragma or builder option (`index_method/fts/mod.rs:146-153`).

## Decision

### 1. Connections: three long-lived roles, sized per role; no pool, no per-read connect

**Recommendation.** One reader checkout owned by `LocalStore` for the UI's list, reader and sidebar reads (behind a small semaphore, two or three, since a turso `Connection` serialises its own operations); one checkout per sync lane for the life of the wave, as `engine.rs:2708-2725` already does; one for the settle path and one for the body indexer. `PER_CONNECTION` splits into an interactive variant at `-65536` and a background variant at `-4096`, and the pragma batch routes through `sql::batch` so the counting seam sees it (`crates/postio-storage/src/sql.rs:256-270`; today `Store::connect` calls `execute_batch` directly, `store.rs:617-619`, and the five statements are invisible to every gate). This is #1602's shape and it is the right one; what this ADR adds is the reason the cache size per role matters *less* than the count, and a rule about the write gate.

**What #1602's landing did, against this.** `Store::read` keeps three warm readers behind a semaphore and `LocalStore::read` and the search `ask` take turns on them; `Store::connect_background` sets `-4096` for the engine, the indexer and the session's housekeeping; and connections are counted process-wide by `test_support::counting::checkouts()` rather than by routing the pragma batch through `sql::batch`, which stays open here.

**Why.** The engine's invalidation is wholesale, not per page (`pager.rs:3198-3202`). During a first sync the writer commits every 9 ms unit (`crates/postio-sync/src/initial.rs:120,128`), so a reader's cache is emptied before nearly every read and a 64 MiB cap never fills from the UI side; a lane writing alone for two hours is the one cache that does saturate. So #1602's "five caches at 64 MiB" is an upper bound, and the win from long-lived readers is mostly *between* syncs — the idle, scrolling case where the working set stays decrypted (see 5). The `WriteGate` (`store.rs:136-266`) orders Postio's writers and never touches a cache; it stays exactly as it is, and interactive reads keep going through a reader, never through `interactive_write()`, because under WAL a reader takes a snapshot and never waits on the gate (#1587, 2026-09-21 comment). Dropping a connection frees its cache (`connection.rs:579` rolls back and releases), which is why the background variant at 4 MiB is the cheap half and lands first.

**Upstream.** `Database::_shared_page_cache` (`database.rs:562`) is constructed at `:680`, stored at `:714`, and read only for a `Debug` line (`:638`); `Connection::_shared_cache` (`connection.rs:405`) is set `false` at `database.rs:2409` and never read. Two fields named for SQLite's shared-cache mode and neither wired: a placeholder, not a plan I can verify. The ask upstream is concrete and small — either honour `_shared_page_cache` for connections opened with a flag, or make the invalidation at `pager.rs:3198` per frame rather than whole-cache — and Postio's three-connection shape is right whether or not it arrives.

**Rejected.** A pool of N connections with a shared cap: turso has no pool and each member would still carry its own cache. One connection per purpose with 64 MiB everywhere: the lanes gain nothing from clean pages they write through. Per-read connect as today (`local.rs:545`; two checkouts per list page, `local.rs:324-342` and `:360`): a fresh pager, an empty cache and five pragmas per read, invisible to the gates.

### 2. Aggregates: a column, or a bound range, and a plan gate that names its columns

**The rule.** On this planner an aggregate is cheap only when it is (a) a column read, or (b) a range over an index whose *every* leading key column is bound. There are no partial indexes to read (`docs/notes/2026-09-12-…`), and `counting::scans` filters on `SCAN` only (`crates/postio-storage/src/test_support/counting.rs:142-160`), so a one-column `SEARCH` that walks the rest of a wide index is invisible to it — the "scan wearing a seek's clothes" of #1587 (`docs/notes/2026-09-21-a-scan-wearing-a-seeks-clothes.md`, on `origin/feature/macos` at `c74e285f`, not yet on `main`). So: any count a list asks for **per page** becomes a maintained column; any existence check on a hot path gets a whole index whose bound columns are asserted; and the gate is an `EXPLAIN QUERY PLAN` assertion naming the bound columns, beside a two-size counted fixture (the `startup_reads` shape, `crates/postio-app/tests/app_suite/startup_reads.rs`). `scans().is_empty()` alone is not a gate.

**The four aggregates.** (i) The folder thread count (#1607, `threads.rs:1095-1125`) becomes `mailboxes.thread_count`, maintained by the trigger family at `schema.rs:800-870` — it comes free with the table in 3, and the count witness (`local.rs:92-105`) then holds the answer rather than a proxy for it. (ii) Flagged, Account and Unified `count(*)` (#1614) are answered from `MailboxRepository::account_counts` (`mailboxes.rs:463-480`), which already sums the four cached columns; no new column. (iii) `corpus_complete` (#1612) becomes `mailboxes.bodies_owed`, incremented on insert (`body_state` defaults to `'not_fetched'`, `schema.rs:416`) and moved by an `AFTER UPDATE OF body_state` trigger — a write that already happens once per body on the backfill path. Rejected for it: a whole `(account_id, body_state)` index, which adds an index entry to every message insert on the path #1587 is still shrinking, to answer a boolean the sidebar's mailbox rows can carry. (iv) The unified count (#1610, `threads.rs:639-670`) cannot be a column: its `NOT EXISTS` partner test coalesces across accounts. It gets the folder scope's witness cache with `sum(total_count) FROM mailboxes` as the one-statement witness, so it is counted once per change rather than once per page. `draft_counts` (#1614) is a fifth of the same family: make `idx_messages_send_state` cover `(account_id, send_state, deleted_locally)` and gate the plan on both columns bound.

### 3. The deep offset: a materialised `mailbox_threads` table, by trigger

**Recommendation.** A table with one row per `(mailbox_id, thread_id)` carrying the representative's sort key (`last_at`, `rep_message_id`) and the folder slice's aggregates (`unread`, `flagged`, `has_attachments`, `member_count`), maintained by `AFTER INSERT/DELETE/UPDATE OF mailbox_id, thread_id, seen, flagged, has_attachments, deleted_locally, snoozed_until ON messages`. The folder window becomes `SELECT … FROM mailbox_threads WHERE mailbox_id = ? ORDER BY last_at DESC, rep_message_id DESC LIMIT 50 OFFSET n` over an index `(mailbox_id, last_at DESC, rep_message_id DESC)`: an index-only walk, the shape #638 measured at 3.58 ms for a 50,000-row jump once the filter columns were in the index (`docs/PERFORMANCE.md`, "Interaction"). The four correlated subqueries per row (`threads.rs:1044-1052`) go, the `NOT EXISTS` in `explain` (`:1054-1062`) goes, `count(*)` over the range is index-only and `mailboxes.thread_count` is its cheaper twin, and `Marks` (`local.rs:172-247`) stays as an optimisation that is no longer load-bearing — an archive that drops every mark (`local.rs:227-232`) costs one index walk, not a 786 ms recount.

**The write cost, honestly.** Per message write, the trigger does one seek on `idx_messages_thread_mailbox` for the newest member and one aggregate over the folder slice, both bounded by the conversation's size in that folder — the same work the page does per row today, done once at the write instead of on every page. After #1587's fix the base path is 1.0–2.7 ms per row to 24k messages (its 2026-09-21 table); this adds two bounded statements inside a trigger and must be measured on `examples/insert_cost_curve.rs` (on `feature/macos`, not `main`) before landing, with the fts column of that table as the ceiling nothing may approach. `MEMBER` reads the clock (`threads.rs:268`); a materialised row is right as of its last write, and `wake_due` (`messages.rs:1262-1290`) clears `snoozed_until` when a snooze comes due, which fires the trigger — the same window the count triggers already accept.

**Rejected.** Sampled cursors seeded in the background: seeding them walks the `NOT EXISTS` window, which *is* the 786 ms count, and `Marks::check` drops everything on every total change — during a sync, every 500 ms tick (#1607). A representative flag on `messages` itself: the same maintenance, and the page still pays its per-row aggregates. Doing only #1607's request de-duplication: worth doing as UI wiring, but it does not remove the walk.

### 4. Full-text memory: patch the budget, ask for the knob, shrink the documents; do not move out

**Recommendation.** Three things, in order. Carry a patch on the pinned pre-release pinning `FTS_MAX_RETAINED_CACHE_BYTES` (`mod.rs:153`) to 32 MiB, and file upstream for a builder option: the test-only override at `mod.rs:159-175` (feature `test_helper`, `Cargo.toml:80`, thread-local so useless to a tokio runtime) shows upstream already treats it as tunable. Measure the body index's actual bytes with `index_suite/body_index_size.rs` on the reference store, because the retained set is bounded by the smaller of index size and 192 MiB per attachment, and there are two attachments (`crates/postio-index/src/index.rs:753,769`). Then shrink what is indexed: `index_body` folds the whole body with no cap (`index.rs:294-298`), and `postio-body`'s quote folder already knows which lines are quoted replies — strip them before folding, and cap the folded text per document. Two more transients to know about: the segment writer takes a 64 MiB arena per build (`mod.rs:125`, used at `:1930`) on every 200-body batch (`crates/postio-session/src/lib.rs:1144`), and the write-path auto-merge rewrites tiers at 100 KiB, 1 MiB, 100 MiB and 1 GiB (`mod.rs:2120`).

**Lazy attachment does not help where it hurts.** Segments are loaded on the first cursor (`mod.rs:1262-1282`) and the `FtsShared` cache is per attachment across connections (`mod.rs:520-521`, created at `:794`), so nothing is resident until a search or a write. During a first sync the body indexer writes every 200 bodies, and a merge reads the tiers it merges — that is when the cache fills, and closing the attachment between searches would not change it.

**Why not a tantivy index Postio manages.** For the record: before ADR 0038 the project had FTS5 inside SQLCipher, never a standalone tantivy; `specs/004-turso-store/spec.md` says FTS5 "has no counterpart here, so it is rewritten" onto the engine's index. Moving out would cost: an encrypting `tantivy::Directory` (`tantivy-0.26.2/src/directory/directory.rs:107`) of Postio's own, because ADR 0014 Q1 rules out a plaintext index over encrypted bodies and `MmapDirectory` is plaintext files; a second commit domain beside the store's transaction, with the `message_search_bodies` presence-is-the-record pattern reinvented as a journal; and `fts_match` leaving SQL, so scopes, facets and ordering (`executor.rs:543-566`) become id-set joins in Rust. What it would buy — merges off the write transaction, the 9–13 ms/row constant of #1587 — is worth having, and it is available without leaving the engine: move the metadata index's writes to a background drain the way bodies already moved (`docs/notes/2026-09-14-seven-improvements-…` §1), which #1587 carries. And the memory problem does not leave with the index: an encrypted directory cannot mmap either, so segments decrypt into the heap — the engine's shape, owned by us.

### 5. Encryption: keep the codec; make the reader cache long-lived so it rarely matters

**Recommendation.** Keep the page codec. ADR 0014 was the maintainer's decision (#143), fscrypt was rejected there for reasons that still hold (no fscrypt on the btrfs development machine, per-machine setup, a posture true only on some filesystems), and ADR 0020's strongest argument — a directory of files leaks sizes and mtimes even encrypted — applies to any plaintext index. The cost is real and bounded: a decrypt per cold page, allocating a fresh `Vec` (`storage/encryption.rs:778-813`) that `decode_page` copies again (`storage/page_transform.rs:182-192`; the `todo(v)` at `:181,189` says upstream intends in-place transforms). But it is not where the felt time is: #638 found `cache_size` from 16 to 256 MiB moved the encrypted jump 207 → 213 ms, and #619 found the unified page identical on a plaintext store. The cipher multiplies cold walks, and 2 and 3 remove the walks. What 1 adds is that the working set stays decrypted between interactions instead of being rebuilt per read. Re-measure the `store` startup phase once 1 lands; that number has not been taken on this engine (`PERFORMANCE.md`).

**Rejected.** Dropping the codec for filesystem encryption: not this ADR's to reopen, and it would change memory only through mmap, which the engine does not do — I found no mmap path in `storage/pager.rs`, but did not read all 6,600 lines.

### 6. Allocator: a three-way measurement, then a build feature, not a runtime variable

**Recommendation.** `postio-app` links `mimalloc = "0.1"` (`crates/postio-app/Cargo.toml:25`; 0.1.52 in `Cargo.lock`), whose `libmimalloc-sys` 0.1.49 builds mimalloc v3 unless the `v2` feature is set (`build.rs:8-12`). v3 defaults `allow_thp` to 1 everywhere but Android (`c_src/mimalloc/v3/src/options.c:103-108`), `madvise`s `MADV_HUGEPAGE` on its arenas (`prim/unix/prim.c:414-421`), purges after 1,000 ms (`options.c:140`) and reserves arenas 1 GiB at a time (`options.c:148`). The `no_thp` feature defines `MI_NO_THP` at build time (`build.rs:99-103`). Measure before choosing: the same seeded first sync under (a) the current build, (b) `features = ["no_thp"]`, (c) `std::alloc::System`, recording `VmRSS`, `RssAnon`, `AnonHugePages` from `/proc/self/smaps_rollup` and `VmHWM` at three moments — after open, after the sync, after 60 s idle — plus the sync's wall time, because THP buys TLB hits and 1's wholesale cache clears hand freed pages to the allocator in exactly the 4 KiB-at-a-time pattern that splits huge pages (#1606). Ship `no_thp` if it recovers ≥ 50 MB at ≤ 5% sync time; keep mimalloc either way, since `main.rs:14-17`'s reason (small-allocation churn from the page cache and the index) is the engine's own and glibc's per-thread arenas inflate on a tokio runtime in their own way.

**Rejected.** `MIMALLOC_ALLOW_THP=0` as an environment variable: `flatpak/dev.postio.Postio.json:10-18` carries no runtime `env` in `finish-args`, and a build decision should not live in a launcher.

### 7. What to measure first, and the nightly that keeps it honest

First, and cheapest: a `connections` counter in `counting::Counts`, incremented in `Store::connect`, asserted per list page and per verb (mark-read, archive, undo) — #1602's acceptance, and the number that settles whether its 64 MiB × 5 arithmetic is real given `pager.rs:3198`. Second: plan gates naming bound columns for every per-page or per-message statement — `count_of`, `corpus_complete`, `draft_counts`, `wake_due` (`messages.rs:1268-1272` records the planner declining `idx_messages_snoozed_due` under an `ORDER BY`), and the new `mailbox_threads` window. Third: for each aggregate that becomes a column, the two-size counted fixture asserting equal statements and rows and no `SCAN`, which is what a column read guarantees by construction. The one nightly: #1503's RSS plateau as a `POSTIO-MEASUREMENT` module under `--profile nightly` (`.config/nextest.toml`), extended per #1606 — a seeded first sync of ~10k messages, `/proc/self` sampled at the three moments above, with the body index present and absent, and the connection count printed beside it. Relative assertions only (final against warm), a control that retains every body and is seen to blow the band, and a `postio-diag census` before and after on the reference store for the field number.

## Consequences

- A schema change: `mailbox_threads`, `mailboxes.thread_count`, `mailboxes.bodies_owed`, a covering `idx_messages_send_state`. No migration — the fingerprint moves and stores resync (ADR 0038; CLAUDE.md, "No backwards compatibility").
- `LocalStore` owns a reader; `Store::connect` grows a `connect_background`; `Checkout`'s doc ("make one per unit of work", `store.rs:608-612`) is rewritten to say the opposite.
- The write path gains a trigger with two bounded statements per message; `insert_cost_curve` is the gate and its fts column the ceiling.
- A patch on the pinned `turso_core` and two upstream asks (the retained budget knob; per-frame or shared cache invalidation), each filed with the measurement that motivates it.
- `docs/PERFORMANCE.md`'s memory table and `store` phase are re-taken on this engine after 1, 3 and 6 land.

## What is deliberately left out

- Moving the metadata full-text index off the write transaction: #1587 carries it and ten-plus test files depend on trigger-immediate indexing.
- The Blitz question (#1543): the reader's web processes are separate PIDs and out of this ADR's memory accounting.
- Facet consolidation into one materialised match set (#1612 §2, with #1526): a `postio-index` change that this ADR's connection rule makes cheaper but does not decide.
- **Not verified:** upstream's intent for `_shared_page_cache`; whether the page cache's per-entry overhead or the 3 MiB buffer-pool arena (`storage/buffer_pool.rs:130,136`) changes the per-connection arithmetic — page buffers beyond the arena are heap, but I did not trace the fallback; the body index's actual size on the reference store; and every wall-clock figure above, none of which has been re-taken on this engine.
